# Migrating skill_stock_analysis to NextGen: feasibility and gaps

Source examined: `/Users/raj/projects/quotes/skill_stock_analysis/` (~30 Python files, `SKILL.md`, `skill.json`) plus its one external dependency, `/Users/raj/projects/agents/email_agent.py`. This report covers what the skill actually does, how it would map onto NextGen's 13 node types, and — the important part — exactly where that mapping breaks down and what would need to be built first.

## What the skill actually does

This is considerably more than "analyze a stock and email a recommendation." It's a small autonomous trading-research system with five distinct subsystems:

**The core analysis loop** (`analyze_stocks.py`, wired up via `skill.json`/`analyze.sh` as the thing that actually runs): reads a ticker list from `stocks.csv`, and for each ticker — fetches 1 year of price history from `yfinance`, computes RSI/CMF/MFI plus a "market profile" (POC/VAH/VAL, essentially a volume-weighted price distribution), computes a volatility-based stop-loss, runs a 1000-path Monte Carlo (geometric Brownian motion) price projection, fetches recent news from the MarketAux API filtered to a hand-picked list of credible domains, and assembles all of that plus a persistent `ReflectiveMemory.md` file into one large prompt sent to an LLM for a Buy/Sell/Hold call. The LLM's answer is then passed through a **quantitative gatekeeper** (`validator.py`) that can override a Buy recommendation to Hold if RSI/price-vs-SMA50/CMF don't independently confirm it. Every ticker's outcome updates a running paper portfolio and a recommendation log, and the whole batch is written to a Markdown report and emailed out.

**A second, more advanced version of the same loop** (`trading_core.py`) exists in parallel — same shape, but adds real position sizing (volatility-adjusted, plus a separate Kelly-criterion calculator that isn't actually called from anywhere), a `StopLossManager` that tracks open positions with bracket stop-loss/take-profit levels, and a `CircuitBreaker` that halts trading after consecutive losses or a daily/weekly drawdown limit. **This file is not wired into `skill.json` or `analyze.sh` — only `analyze_stocks.py` is the live entry point.** Worth confirming with the project owner whether `trading_core.py` is the intended eventual replacement or dead-end experimentation, since it changes what "the skill" means for a migration.

**Performance evaluation and reflection** (`evaluate_performance.py`, `reflect_enhanced.py`, `track_progress.py`, `check_ticker_accuracy.py`, `query_stats.py`): separate, independently-triggered scripts that mark-to-market every logged recommendation, compute Sharpe ratio/max drawdown/profit factor/win rate, benchmark against SPY, and — weekly — feed all of that back through another LLM call to generate specific "FOR TICKER: do X because Y" rules, which get written back into `ReflectiveMemory.md` and read by the *next* run of the core analysis loop. This is a genuine learning loop across separate, time-separated workflow executions, not just prompt engineering within one run.

**An email-based command-and-control channel** (`inbound_manager.py`): polls an IMAP inbox for whitelisted senders sending `cmd: <command>` or `save: ...` subject lines, validates the command against a strict allow-list, and — notably — implements a propose-then-confirm pattern: a new command is queued and replied to with a `[PENDING APPROVAL] ID:xxxx`, and only executes once the sender replies with `cmd: confirm ID:xxxx`. This is functionally a hand-rolled human-in-the-loop pause/resume mechanism, just over email instead of chat.

**A portfolio/risk layer and reporting utilities**: `portfolio.py` (paper position tracking), `safety_watcher.py` (5%+ move alerts on open positions), `log_manual_trade.py`, `get_portfolio_summary.py`, `list_reports.py`, `resend_reports.py`, `backtest.py` (a simple historical replay of the validator gate), plus test/integration scripts (`master_integration_test.py`, `e2e_mock_test.py`) that aren't part of the runtime pipeline.

State is spread across eight separate JSON files under `logs/`: `progress.json`, `portfolio.json`, `active_positions.json`, `trade_history.json`, `performance_log.json`, `TickerRegistry.json`, `pending_commands.json`, `email_history.json` — each read and written by different scripts, across different, separately-triggered runs.

## Proposed NextGen workflow shape

The core analysis loop maps reasonably cleanly onto a graph like this: an entry node (see the trigger gap below) feeds a **Loop node** iterating the ticker list; each iteration's body does market-data-and-indicator fetching, then a **Decision** chain or two, into an **LLM node** with the assembled prompt, then a **Decision** chain reproducing the validator gate (RSI 40–70, price > SMA50, CMF > 0 — each as its own Decision node, chained), landing on a **Variable node** write for that ticker's outcome, looping back to the Loop node. Once all tickers are done, a **Merge node** (or just the Loop's own aggregated "done" output, since your Merge node's use case is parallel branches rather than sequential loop results) feeds a final report-assembly step and a **Response** node.

The weekly reflection and performance-evaluation flows are naturally separate NextGen workflows (not a single graph) — they're already independently triggered in the original, and NextGen's per-run model doesn't lose anything by keeping them apart. Each would be its own Input → data-aggregation → LLM (for reflection) → Variable-write → Response chain.

Where this proposal gets genuinely uncertain is everything that isn't "call an LLM and route on the result" — the market-data fetch, the indicator math, and the cross-run state. Those are covered in detail below because none of them are a clean fit for any of the 13 existing node types as they stand today.

## Node-by-node mapping

| Skill component | Best NextGen fit today | Fit quality |
|---|---|---|
| LLM recommendation call | LLM node | Good — direct fit, provider abstraction already anticipates this |
| MarketAux news fetch | API node | Good — plain REST call, templated URL, credential_id for the API key |
| Per-ticker iteration | Loop node | Good — this is exactly what it's for |
| Validator gate (RSI/SMA/CMF thresholds) | Chained Decision nodes | Workable — one binary comparison per node, 3 nodes instead of 1 compound check |
| Circuit breaker / consecutive-loss pause | Decision node, fed by a durable counter | Blocked — see cross-run state gap below |
| yfinance price history + RSI/CMF/MFI/market-profile/GBM projection math | No good fit — see gap below | Blocked |
| Stop-loss / Kelly / position-sizing calculations | No good fit — same numeric-library gap | Blocked |
| Portfolio position tracking, active positions, trade history | No good fit — see cross-run state gap | Blocked |
| ReflectiveMemory.md read/write across runs | No good fit — same gap | Blocked |
| Daily 8am/4pm scheduling | No native equivalent — see trigger gap | Blocked |
| Email report delivery | API node (if using an email-sending HTTP API) or a new Tool implementation wrapping SMTP | Workable with one addition |
| IMAP inbound command + approve/confirm | No equivalent channel — see trigger gap | Blocked as designed; the *pattern* (pause for confirmation) already exists via Input nodes |
| Credential storage (SMTP password, Gemini key, MarketAux key) | Credential model exists, no UI yet (tracked as your own T084) | Backend ready, UI missing |

## Gaps, in order of how much they block the migration

**1. No native scheduled/cron trigger.** The skill's entire premise is "run automatically twice a day." NextGen's Constitution Principle II is explicit that chat is the runtime interface — every workflow today starts because a person opens the chat sidecar and picks it, or an external caller hits an API endpoint. There's no workflow-level "run this at 08:00 and 16:00 daily" primitive in the app itself. This is the single largest blocker for the "autonomous agent" framing in `SKILL.md` — without it, every run is a chat-initiated `start_workflow` call, i.e. someone or something has to trigger it, which just relocates the scheduling problem outside NextGen (e.g., a cron job that calls the chat API) rather than solving it inside the tool. Worth deciding deliberately whether that's acceptable (cron calls into NextGen's API) or whether NextGen should grow its own scheduler — the latter is a real feature addition, not a workaround.

**2. The Code node's sandbox can't run this skill's actual math.** This is the gap most likely to be mis-diagnosed, so it's worth being precise. The Code node's subprocess worker (`app/sandbox/_worker.py`) allows exactly nine stdlib modules — `json, math, re, string, datetime, statistics, itertools, collections, decimal` — enforced by a guarded `__import__`. `pandas`, `numpy`, and `yfinance` are absent, and this is deliberate (Constitution VI: no network access, hard resource limits, RestrictedPython execution) — it's the correct design for a sandbox meant to run arbitrary end-user-authored snippets. But the skill's indicator math (RSI/CMF/MFI, market profile, Sharpe ratio, max drawdown, GBM Monte Carlo projection) is entirely numpy/pandas-based, and the market-data fetch needs `yfinance` and outbound network access the Code node explicitly denies by design. **The fix isn't loosening the Code node's sandbox** — that would weaken a guarantee Constitution VI calls non-negotiable, for every workflow in the system, to accommodate one skill. The fix is recognizing that every other node type (`llm_node.py`, `api_node.py`, `memory_node.py`) is *not* sandboxed — they're trusted, developer-authored backend modules that already import whatever's `pip install`ed into the image (LangChain, Chroma, httpx). A new node type built the same way — say, a "Market Data" node whose `execute()` function is a normal trusted Python module using `yfinance`/`pandas`/`numpy` freely, registered via `register_node_type` exactly like the existing ones — is the idiomatic solution. That's real implementation work (new Pydantic config, new executor module, new canvas component, `yfinance`/`pandas`/`numpy` added to the backend image), not a config change.

**3. No durable, structured, cross-run state store.** This is the least obvious gap but arguably the biggest one architecturally. The skill leans on eight separate JSON files that persist *across* separate workflow executions: today's portfolio positions need to be readable by tomorrow's run; the circuit breaker needs the last 5 trades' outcomes from however many days back; the weekly reflection needs a week of daily eval files; `ReflectiveMemory.md` written by Sunday's reflection run needs to be read by Monday morning's analysis run. NextGen's Variable node is explicitly scoped per Constitution ("a named, **run-scoped** value store") — it doesn't survive past the run that set it. The Memory/Retrieval node is the closest thing to durable storage, but it's read-only from the canvas (querying a Chroma vector store) with no write-side node at all — ingestion only happens through a separate REST endpoint (`POST /api/vector-stores/{name}/documents`), and semantically it's built for unstructured-text similarity search, not structured key-value state like `{"AAPL": {"position": 3, "avg_price": 187.20}}`. Reproducing the portfolio/circuit-breaker/reflective-memory pattern faithfully needs a new primitive — a durable key-value or structured-record store with both a read node and a write node, scoped across runs rather than within one. This is the one gap I'd flag as needing a real design decision (and likely a constitution discussion, since "run-scoped" for Variable nodes was a deliberate choice) before implementation starts, not just an additive node type.

**4. Only the Ollama provider is implemented.** `llm_utils.py`'s LOCAL/QUALITY split (Ollama primary, Gemini fallback on repeated failure) has no NextGen equivalent today — `app/providers/base.py`'s `ModelProvider` abstraction is deliberately ready for this ("adding a provider means adding a class here, never touching workflow schemas"), but `_get_provider()` in `llm_node.py` only recognizes `"ollama"` and raises for anything else. This is a scoped, contained gap: one new `GeminiProvider` class. The automatic "3 failed local attempts → fall back to a different provider" behavior isn't a provider concern though — that would need composing a Retry node with a second LLM node bound to the Gemini provider, wired off the first LLM node's failure port, which the existing dual-output pattern supports today once the provider itself exists.

**5. Templating resolves whole values only, no dot-path into nested JSON.** `{{previous}}` always stringifies the *entire* last node output; there's no `{{previous.rsi}}` or similar field-access syntax in `app/graph/templating.py`. The skill's prompt construction pulls in many individually-formatted fields (ticker, weekly return, indicator values, POC/VAH/VAL, stop-loss, projections by day, RSI, filtered news headlines) into one carefully-shaped string. Reproducing that exact prompt shape on the canvas means either routing each field through its own named Variable node (workable, but a lot of nodes for one prompt) or accepting a less precisely-formatted prompt built from whole-object dumps. A small, scoped enhancement to `resolve_value_reference`/`render_template` to support `{{previous.field.nested}}` would remove this friction and is much lower-effort than gaps 1–3.

**6. Four separate hardcoded plaintext secrets, found while reading the skill.** `analyze.sh` and `email_agent.py` both hardcode the same Gmail app password in plaintext; `inbound_manager.py` hardcodes it a third time; `llm_utils.py` hardcodes a Gemini API key; `trading_core.py` hardcodes the MarketAux API key (a second, different value than the one loaded from `.env` in `analyze_stocks.py` — worth checking which is actually current). This isn't a NextGen gap, it's a pre-existing issue in the skill itself, but it's the clearest possible illustration of exactly what Constitution VI's encrypted-credential-storage requirement is for, and every one of these four values should move into NextGen's `Credential` model (already implemented) rather than being carried over into any migrated workflow. Flagging this now since it directly overlaps with the credential-management-UI gap already tracked as T084 in `ANTIGRAVITY_HANDOFF.md` — building that UI would give this migration a real place to put these secrets.

**7. Decision node is a single binary comparison; the validator's compound gate needs chaining.** Minor by comparison to the above, but worth noting precisely: RSI-in-range AND price-above-SMA50 AND CMF-positive is expressed in `validator.py` as one function with three independent checks. On the canvas this becomes three chained Decision nodes (each node's "true" output feeding the next check), which works correctly but is visually more verbose than the source. Not a blocker, just a design note for whoever builds the graph.

## Recommendation

Don't attempt a full migration in one pass. The core analysis loop (fetch → indicators → LLM → validate → log) is the part worth proving out first, and it's blocked on exactly one prerequisite: a new trusted "Market Data" node type (gap 2) — everything else in the core loop (LLM, API, Loop, Decision, Variable, Response) is ready today. Get that working end-to-end as a manually-triggered NextGen workflow before touching scheduling (gap 1) or cross-run state (gap 3), since those two are the gaps most likely to need a real design decision rather than an afternoon of implementation. The email inbound/approval channel (gap 1's IMAP half) and the automated circuit breaker are the parts I'd defer longest — they depend on gap 3 being solved first, and the circuit breaker specifically depends on trade outcomes that don't exist until the core loop has been running for a while.
