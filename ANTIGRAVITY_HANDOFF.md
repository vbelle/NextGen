# Handoff: continuing NextGen

This is a handoff to whichever agent picks this project up next. It covers what NextGen is, exactly what's done vs. open, the gotchas that cost real time during manual testing, how to verify changes before pushing, and where I'd focus next if I were continuing this myself. Read this before touching code — most of the mistakes it warns about were made once already.

## What this is

NextGen is a self-hosted, agentic workflow builder: a React Flow canvas for wiring together 13 node types (Input, LLM, Response, Decision, API, Variable, Code, Retry, Loop, Memory, Tool, Sub-workflow, Merge) into a graph, compiled to a LangGraph `StateGraph` and run through a chat interface. Runs entirely on Docker Compose, defaults to a bundled Ollama container for local LLM/embeddings, no other external calls.

Repo: `github.com/vbelle/NextGen`. Built via Spec Kit (`.specify/`, `specs/001-workflow-builder/`) — `constitution.md`, `spec.md`, `plan.md`, `tasks.md` are the actual source of truth for scope and design decisions, not this document. Read `constitution.md` first; its 7 principles (self-hosted/small-team, chat-is-the-runtime, LangGraph-non-negotiable, canvas-is-source-of-truth, provider-agnostic models, sandboxed+encrypted-secrets-non-negotiable, every-run-audited) explain *why* the code is shaped the way it is, and any change that violates one needs a documented constitution amendment, not a silent workaround.

## How this session left things

Backend, from oldest to newest: Merge node (13th/final node type) fully implemented and tested; then the View code panel's LangGraph tab was extended to show each used node type's *real* `execute()` source (via `inspect.getsourcefile`) plus `tool_registry.py` when a Tool node is present, not just the `add_node`/`add_edge` wiring skeleton it showed before. Last commit pushed: `f3834b4`.

**Read `codegen.py` before extending it further.** It has a documented, deliberate design tension worth preserving: it's *lenient* (unknown node type → a "could not read source" comment, not a crash) because it must render mid-edit, on an unsaved canvas, before the graph is necessarily valid — unlike `compiler.py`, which validates strictly because it's about to actually run something. If a future change makes codegen stricter "for consistency" with the compiler, that will break the live-preview-while-editing property, which is the entire point of the panel per the user's own request this session ("I want to see the complete code the flow generates" — asked for *while editing*, not just after a successful save).

**codegen.py and credentials, specifically**: it now inlines whole source files by path. If a future node type's source ever contains anything credential-adjacent inline (it shouldn't, given the `_resolve_credential`/`crypto.py` pattern — credentials are always resolved by ID at runtime, never embedded in source), this panel would render it straight into the browser. Worth a specific look during the T087 security pass: confirm no node's `execute()` function ever has a literal secret in it (should always be true by construction) and confirm the codegen panel doesn't leak *resolved* values from a specific run (it shouldn't — it renders static source, not a run's actual data — but this is exactly the kind of adjacent-feature interaction a grep pass is for).

## Things that cost real time — read before you hit them again

- **Docker image rebuilds, not restarts.** `./nextgen.sh start`/`restart` do not pick up code changes — the frontend is baked into the image at build time and the backend runs from what was `COPY`'d in. Only `./nextgen.sh rebuild` does. This tripped the user twice on the exact same "View code shows nothing" symptom — second time was just a missed rebuild, not a regression. If a bug report exactly repeats one already fixed, ask about rebuild status before re-debugging.
- **Python version split.** Local dev/CI sandbox here runs 3.10; the production Dockerfile pins `python:3.11-slim` (LangGraph/LangChain requirement, comment in `Dockerfile` explains why). A chunk of the integration test suite (anything using `interrupt()` for human-in-the-loop pausing, e.g. `test_merge_node.py`'s main scenario) is decorated `requires_py311` and **skips silently in this sandbox** — 15 skips is normal here, not a gap, but it means those tests have only ever really run inside the actual Docker build, not in this dev loop. Don't trust "all tests passed" from this sandbox alone for anything touching `interrupt()`; either run under 3.11 or spot-check inside the built container before trusting a change to paused/resumed execution.
- **Ollama models are never auto-pulled.** Typing a model name into an LLM node config does nothing by itself — Ollama only serves models already pulled into the container (`./nextgen.sh pull <model>`, which wraps `docker compose exec ollama ollama pull <model>`). A blank/wrong-looking LLM node response is very often just an unpulled model, not a bug — check `docker compose exec ollama ollama list` first.
- **Tool binding is eager and all-or-nothing.** `llm_node.py`'s `execute()` resolves *every* bound tool via `get_tool_implementation` in a list comprehension *before* generation starts. One bad `implementation_ref` fails the entire LLM node call, not just that tool. If someone reports "my LLM node stopped responding entirely" after adding a tool, check `implementation_ref` against `tool_registry.py`'s actual registered names first — it's a very easy typo to make since the tool node's config is free text, not a dropdown validated against the registry.
- **Small local models (llama3.2 and similar) are not reliable tool-callers.** Multiple manual-testing sessions here hit garbled pseudo-tool-call text or empty `[]` responses from compound prompts (multi-part decomposition + conditional tool use + strict JSON output all at once) — this is a capability ceiling of the model, not an app bug, and it's worth being able to tell the two apart quickly. If tool-calling looks broken, try a strictly simpler prompt against the same wiring before assuming the code regressed.
- **CSS flex containers need a definite `height`, not just `max-height`.** Bit the View code modal twice. A `flex: 1 1 0` child inside a column with only `max-height` set (no `height`) has nothing definite to grow into and silently collapses to 0px while sibling non-flex content (headers) stays visible — looks exactly like "nothing renders" rather than a layout bug. Worth a quick audit of other modals/sidecars for the same pattern before it surfaces as another confusing bug report.
- **Verification workflow that's been working well**: for backend changes, copy the mounted project into a scratch copy (this session used `/tmp/nextgen-backend-test`), run `pytest`, `ruff check`, `black --check` there, fix forward, then sync the fixed files back to the real path — never edit only in the throwaway copy and forget to sync back (happened once this session, caught before pushing). For frontend, the equivalent is `tsc --noEmit`, `vite build`, `eslint`, `prettier` in a persistent scratch copy. Always test in isolation (a single new test file run alone) in addition to the full suite — this session's codegen work had a real bug (`codegen.py` not forcing node-type registration like `compiler.py` does) that only the full suite masked, because some earlier test file happened to trigger registration first. A change that only passes *in combination* with unrelated tests is not verified.
- **Force-push workflow**: this session's push process builds a fresh scratch copy from the mounted path, `git init`s it clean, commits, and force-pushes `main` — it does not preserve the mounted repo's own local `.git` history (that stays behind, separately, mostly stale). After any push, the standing instruction to the human has been: `git fetch origin && git reset --hard origin/main`, then `./nextgen.sh rebuild` specifically if frontend or backend code changed.

## What I'd focus on next, in order

1. **Credential management UI (T084).** This is the one gap that actually blocks a real use case (any authenticated API call) rather than being pure polish. The backend is fully ready for it — this is a scoped, self-contained frontend task.
2. **`test_quickstart_scenarios.py` (T085).** Turns the 4 scenarios in `quickstart.md` from "things I manually clicked through" into a real CI gate. Given how much of this project's correctness has been validated by hand in chat so far, this closes the biggest verification gap.
3. **Security grep pass (T087)**, specifically re-checked against the new View code panel's source-inlining behavior described above, and against the credential/API-node path.
4. **Clean-machine validation (T086)** once 1–3 are done, as a final release gate — this is the step most likely to surface an environment assumption nobody's questioned yet (e.g. does `.env.example` actually have everything a fresh clone needs, does the first-run experience make it obvious you need to `ollama pull` before anything works).
5. **Responsiveness check (T089)** — lower priority; nothing in manual testing has suggested this is actually a problem, it's just never been measured against the plan's explicit ~500ms goal.

Beyond the Final Phase, ideas that came up but were deliberately out of scope for v1 per the constitution (worth knowing about, not worth doing without confirming intent first — each would need a constitution amendment, not a silent addition): per-user accounts/SSO instead of the single shared password (Principle I explicitly defers this), additional LLM providers beyond Ollama (Principle V says this should be a config change when it happens — the provider abstraction in `backend/app/providers/` was built with this in mind, worth checking it actually stays swap-in-ready as new node types get added), and a tool-registry UI so tool implementations don't require editing `tool_registry.py` directly (currently the only way to add a genuinely new tool, as opposed to wiring an existing one, is a code change).

## Constitution-driven guardrails to not accidentally violate

These are non-negotiable per `constitution.md`, worth internalizing before making changes that touch them:

- No synchronous "run and block in the HTTP request" path may ever be added — every run is background/async because any node may pause indefinitely (Principle III).
- No workflow authoring path may bypass the canvas — if a feature can't be expressed as nodes+edges, it's not v1 scope (Principle IV).
- The Code node sandbox must never gain filesystem/network access by default, and must keep enforced CPU/time/memory limits (Principle VI).
- No raw credential value may ever appear outside `crypto.py`'s decrypt call site — not in workflow JSON, not in version history, not in logs (Principle VI, and directly relevant to T087 above).
- Every run, every Input-node value, and every node's input/output must stay logged and retrievable per run (Principle VII) — keep this in mind if the audit/log UI (T083) gets reworked, don't accidentally narrow what's captured while improving how it's displayed.
